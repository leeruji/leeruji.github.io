디자이너가 만든 팀 협업 AI 워크플로우

위시리스트 앱 Diggin 팀 프로젝트에서, 흩어진 팀 결정 사항을 기능명세서와 피그마 화면에 반영하는 반복 작업을 AI 에이전트가 팀 규칙대로 처리하도록 설계했습니다.

역할 프로덕트 디자이너 2026.09– 진행 중 사용 도구 Claude · Figma · Google Sheets · GitHub
문제

결정은 여러 곳에서 나오고 반영은 한 사람이 손으로 했습니다

PM, 디자이너, 개발자가 함께하는 사이드 프로젝트라 결정이 한곳에서 나오지 않았습니다. 디자이너 한 명이 이걸 기능명세서와 화면에 하나씩 옮기다 보니 빠뜨리는 게 생기고 형식도 사람마다 달라졌습니다.

AI는 정리하고 대조하고, 결정과 공개는 사람이 합니다

AI 에이전트가 수행사람 디자이너가 확인하는 지점
  1. 1

    결정 사항 전달사람

    메신저 캡처, 피그마 코멘트 링크, 회의 메모를 그대로 넘깁니다. 여러 건이면 AI가 항목별로 나눕니다.

  2. 2

    현재 명세 읽기와 분류AI

    관련 기능 ID와 수정할 열을 찾고 이미 반영된 내용인지 확인한 뒤 확정과 확인 필요로 나눕니다.

  3. ✓

    변경 전·후 미리보기 확인사람

    시트를 고치기 전에 변경 전·후 표와 변경이력에 들어갈 행을 먼저 보여줍니다. 디자이너가 OK해야 다음으로 넘어갑니다.

  4. 3

    명세서 반영과 변경이력 기록AI

    확정은 기능명세에 반영하고, 확인 필요는 기획 확인사항 탭에 이슈로 등록합니다. 모두 PM이 정한 작성 규칙대로 변경이력을 남깁니다.

  5. 4

    정책과 피그마 화면 대조AI

    정책을 체크리스트로 쪼개고 화면을 하나씩 캡처해 맞음, 틀림, 누락, 모호로 판정합니다.

  6. 5

    컴포넌트 변경 시 개발 상태 확인AI

    저장소에서 해당 컴포넌트가 개발 중인지, 이미 구현됐는지, 담당자가 누구인지 확인합니다.

  7. ✓

    개발 전달 코멘트 검토 후 게시사람

    팀 포맷에 맞춘 코멘트 초안을 디자이너가 확인한 뒤에만 피그마에 올립니다.

직접 만든 스킬

팀 규칙을 AI가 읽을 수 있는 지시서로 옮겼습니다

매번 설명하지 않아도 같은 결과가 나오도록, 반복 업무마다 절차와 판단 기준을 스킬 파일로 정리했습니다.

skill / spec-update

기능명세서 반영

  • 모든 문장은 한 칸에 한 줄, 명사형 종결, 마침표 없이 작성
  • 근거가 애매하면 확정이 아니라 확인 필요 쪽을 택한다
  • 기존 확정 정책과 충돌하면 덮어쓰지 않고 충돌 사실을 알린다
  • 디자인 상태만 바뀌어도 개발팀이 볼 수 있게 변경이력을 남긴다
  • 쓰기 직전에 행 위치와 ID를 다시 읽는다 (PM과 동시 편집 대비)
skill / policy-screen-audit

정책 ↔ 화면 대조

  • 명세서의 기능 ID가 아니라 화면 ID로 피그마 프레임을 매칭한다
  • 라벨용 프레임, 긴 글 변형, 추후 확장 섹션은 대조 대상에서 뺀다
  • 여러 화면에 반복되는 문제는 화면이 아니라 컴포넌트부터 고친다
  • 모호하거나 충돌하는 정책은 캔버스에 메모하지 않고 바로 묻는다
rule / component-description

컴포넌트 설명 작성 규칙

  • 용도 → 구성 → 변형 → 주의 순서, 한 줄에 한 정보
  • 속성 이름과 값은 피그마 표기 그대로 쓴다
  • 다른 디자이너의 AI에도 같은 규칙을 전달해 결과물을 통일

확정

명확한 합의가 있으면 기능명세 해당 칸만 수정하고, 연결된 이슈를 해결 처리합니다.

확인 필요

수치 누락, 의견 충돌, 대응 기능이 불분명하면 명세는 건드리지 않고 이슈로 등록합니다.

AI에게 맡기지 않은 것

가장 오래 고민한 건 AI가 멈춰야 할 지점이었습니다

  • 모호한 정책의 해석AI가 그럴듯하게 정하면 틀린 결정이 명세서에 확정처럼 남습니다. 그래서 바로 디자이너에게 묻게 했습니다.
  • 팀에 공개되는 코멘트개발자가 읽고 바로 작업하는 글이라 초안을 먼저 보여주고 승인 후에만 올립니다.
  • 문서 수정변경 전·후 미리보기를 거치지 않으면 시트에 쓰지 않습니다. 남이 쓴 과거 기록을 고칠 때도 같습니다.
  • 새 기능 추가명세에 없는 항목은 AI가 만들지 않고, 추가할지 먼저 묻습니다.
배운 점

AI를 잘 쓰는 일은 프롬프트를 잘 쓰는 것보다, 팀이 이미 가진 암묵적인 규칙을 꺼내서 글로 정리하는 일에 가까웠습니다. 규칙이 명확해지자 AI 결과물뿐 아니라 사람 사이의 협업 방식도 같이 정리됐습니다.
